# WildfireGuardian assisted dispatch — v0.1.0 scientific benchmark

Seven canonical examples plus three supporting cases, each with a tiny
network, its parameters, a hand calculation, the solver's answer, a
pass/fail comparison against **three independent methods**, and the
scientific lesson it exists to carry.

Every number below is generated by `tools/build_benchmark.py`; none is
transcribed. The three methods compared are:

1. the **grid sweep** (sampled at the stated step),
2. the **exact interval solver** (closed form, no time discretization),
3. an **independent brute-force oracle** that shares no search, timing
   or hazard-assessment code with the main solver.

> **Scope.** Every result is *oracle-conditioned physical feasibility*:
> the planner is given the complete future of the hazard scenario. These
> are physical feasibility upper bounds, not operating envelopes and not
> dispatch recommendations. See `docs/ORACLE_FEASIBILITY_LIMIT.md` and
> `docs/CLAIMS.md`.

## A.1. Deterministic round trip - the arithmetic baseline

```
    base ──10──▶ home ──10──▶ shelter
                            egress corridor lost at t = 40
    pickup 5 min
```

**Fixture `a`** — single road

*Parameters*

```
mission 'A-single-road' on network 'A-single-road'
  base      : base
  resident  : home
  pickup p05 = 5 min
  policy    : admission=full_interval, waiting=prohibited, revisits=prohibited, horizon=120 min
  destination shelter
  scenarios : coherent
  threshold : q = 1
  grid      : 0 … 30 min, step 1
```

*Hand calculation*

```
ingress  : [t, t+10]        base -> home, never hazardous
pickup   : [t+10, t+15]     5 min at the address
egress   : [t+15, t+25]     home -> shelter, must be clear THROUGHOUT
           t + 25 <= 40  =>  t <= 15
t_dagger = 40 - 10 - 5 - 10 = 15
```

*Solver results*

| method | feasible dispatch set |
|---|---|
| hand calculation (sampled) | [0, 15] |
| grid sweep | [0, 15] |
| hand calculation (exact) | [0, 15] |
| exact interval solver | [0, 15] |
| independent brute-force oracle (same grid) | [0, 15] |

*Connected components*: 1 &nbsp;&nbsp; *Is a dispatch-by deadline*: yes

**Comparison: PASS** — hand calculation, grid sweep, exact solver and independent oracle all agree.

**Scientific lesson.** The dispatch envelope is set by the **exit** instant of the last hazardous traversal, not by its entry. Everything else in this benchmark is a complication of this one subtraction.

## B. Scenario-weighted success

```
                 ┌─5─▶ north_j ─5─▶┐
    base ─5─▶ home                    shelter      pickup 5 min
                 └10─▶ south_j ─10─▶┘

    nominal      w=0.5   ridge lost at 35, valley at 60
    wind_shift   w=0.3   ridge lost at 20, valley at 60
    south_flank  w=0.2   ridge lost at 35, valley at 28
```

**Fixture `b_ensemble`** — two routes under a three-scenario ensemble

*Parameters*

```
mission 'B-two-routes-ensemble' on network 'B-two-routes'
  base      : base
  resident  : home
  pickup p05 = 5 min
  policy    : admission=full_interval, waiting=prohibited, revisits=prohibited, horizon=150 min
  destination shelter
  scenarios : nominal, wind_shift, south_flank
  threshold : q = 1
  grid      : 0 … 40 min, step 1
```

*Hand calculation*

```
nominal     (w=0.5): north t<=15, south t<=30  -> succeeds t <= 30
wind_shift  (w=0.3): north t<= 0, south t<=30  -> succeeds t <= 30
south_flank (w=0.2): north t<=15, south never  -> succeeds t <= 15
P_success(t) = 1.0 for t <= 15
             = 0.8 for 16 <= t <= 30
             = 0.0 for t >= 31
T at q=1.0 is [0, 15];  at q=0.8 it is [0, 30]
```

*Solver results*

| method | feasible dispatch set |
|---|---|
| hand calculation (sampled) | [0, 15] |
| grid sweep | [0, 15] |
| hand calculation (exact) | [0, 15] |

*Connected components*: 1 &nbsp;&nbsp; *Is a dispatch-by deadline*: yes

**Comparison: PASS** — hand calculation, grid sweep, exact solver and independent oracle all agree.

**Scientific lesson.** P_success is a **sum of coherent scenario weights**, so it is a step function with thresholds where whole scenarios drop out. An independent-edge product would have produced a smooth curve with no threshold at t = 15, and that smoothness would have been fiction.

**Scientific lesson.** **Proximity is not the dispatch envelope.** The base ten minutes closer to the resident runs a 25-minute mission and has the *smaller* feasible set, because its own approach corridor is the one the fire takes first. Mission duration and dispatch envelope are different quantities and can order oppositely.
*Side by side*

| staging point | mission duration | feasible dispatch set | binding constraint |
|---|---|---|---|
| `base_north` (10 min away) | 25 min | [0, 12] | its own approach corridor |
| `base_south` (20 min away) | 35 min | [0, 15] | the shared egress corridor |

Note what is *not* computed: the union of the two sets. Each mission names one staging point; nothing here chooses between them, and the union must not be reported as "the" feasible set for this resident.

## F. Disconnected feasible windows

```
    base ──5──▶ home ──5──▶ shelter
                            egress corridor safe on [0, 12] ∪ [18, 25]
    pickup 2 min
```

**Fixture `f`** — non-monotonic feasibility

*Parameters*

```
mission 'F-non-monotonic' on network 'F-non-monotonic'
  base      : base
  resident  : home
  pickup p02 = 2 min
  policy    : admission=full_interval, waiting=prohibited, revisits=prohibited, horizon=120 min
  destination shelter
  scenarios : reopening
  threshold : q = 1
  grid      : 0 … 20 min, step 1
```

*Hand calculation*

```
egress corridor safe on [0, 12] U [18, 25]
arrive home t+5, pickup ends t+7, egress occupies [t+7, t+12]
  fits in [0, 12] :  t + 12 <= 12            =>  t <= 0
  fits in [18, 25]:  t + 7 >= 18 and t + 12 <= 25
                     =>  11 <= t <= 13
T = {0} U [11, 13]     sup T = 13, but T is NOT an interval
```

*Solver results*

| method | feasible dispatch set |
|---|---|
| hand calculation (sampled) | [0] ∪ [11, 13] |
| grid sweep | [0] ∪ [11, 13] |
| hand calculation (exact) | [0] ∪ [11, 13] |
| exact interval solver | [0] ∪ [11, 13] |
| independent brute-force oracle (same grid) | [0] ∪ [11, 13] |

*Connected components*: 2 &nbsp;&nbsp; *Is a dispatch-by deadline*: **no** — report windows, not a deadline

**Comparison: PASS** — hand calculation, grid sweep, exact solver and independent oracle all agree.

**Scientific lesson.** Feasibility is **not monotone in dispatch time**. Dispatching at t = 5 fails; dispatching at t = 12 succeeds, with no waiting anywhere - only the phase of the corridor's timeline differs. Any summary of the form 'dispatch by 13' asserts that t = 5 works, and it does not.

## G. Myopic entry-only failure

```
                 ┌───── 10 ─────▶┐     fast corridor lost at t = 20
    base ─4─▶ home                 shelter
                 └6─▶ mid ──8────▶┘     slow corridor lost at t = 40
    pickup 2 min
```

**Fixture `g_myopic`** — mid-edge closure, entry-time-only admission

*Parameters*

```
mission 'G-mid-edge-entry-only' on network 'G-mid-edge-closure'
  base      : base
  resident  : home
  pickup p02 = 2 min
  policy    : admission=entry_only, waiting=prohibited, revisits=prohibited, horizon=120 min
  destination shelter
  scenarios : coherent
  threshold : q = 1
  grid      : 0 … 25 min, step 1
```

*Hand calculation*

```
the myopic planner admits the fast corridor whenever it is safe at
the entry instant:  t + 6 <= 20  =>  t <= 14, and prefers it
because it promises arrival at t+16 instead of t+20.
  t <=  4        fast is genuinely clear             -> SUCCESS
  5 <= t <= 14   fast is entered and lost mid-way    -> CAUGHT_MID_EDGE
 15 <= t <= 20   fast is already unsafe at entry,
                 so the slow road is taken instead   -> SUCCESS
  t >= 21        the slow road is entered and lost
                 mid-way as well                     -> CAUGHT_MID_EDGE
T = [0, 4] U [15, 20]
```

*Solver results*

| method | feasible dispatch set |
|---|---|
| hand calculation (sampled) | [0, 4] ∪ [15, 20] |
| grid sweep | [0, 4] ∪ [15, 20] |
| exact interval solver | not applicable |

> Exact solver refused, correctly: the exact solver computes 'a safe plan exists'; under 'entry_only' admission feasibility depends on which plan a myopic planner selects, which is not a per-plan interval constraint. Use the brute-force oracle for that case.
| independent brute-force oracle (same grid) | [0, 4] ∪ [15, 20] |

*Connected components*: n/a &nbsp;&nbsp; *Is a dispatch-by deadline*: n/a

**Comparison: PASS** — hand calculation, grid sweep, exact solver and independent oracle all agree.

**Scientific lesson.** Checking hazard at the entry instant does not merely lose missions - it loses them **by driving into the fire**. Between t = 5 and t = 14 the myopic planner reports a plan right up until the audit, which then finds the responder and the resident caught mid-segment. The hole in its feasible set is manufactured entirely by the wrong semantics.

## J. A feasible window narrower than the sweep step

```
    base ──5──▶ home ──5──▶ shelter
                            egress corridor passable ONLY on [18.3, 23.4]
    pickup 2 min
```

**Fixture `n`** — feasible window narrower than the sweep step

*Parameters*

```
mission 'N-narrow-window' on network 'N-narrow-window'
  base      : base
  resident  : home
  pickup p02 = 2 min
  policy    : admission=full_interval, waiting=prohibited, revisits=prohibited, horizon=120 min
  destination shelter
  scenarios : narrow
  threshold : q = 1
  grid      : 0 … 20 min, step 1
```

*Hand calculation*

```
egress corridor safe only on [18.3, 23.4]
arrive home t+5, pickup ends t+7, egress occupies [t+7, t+12]
  t + 7  >= 18.3  =>  t >= 11.3
  t + 12 <= 23.4  =>  t <= 11.4
TRUE feasible set   : [11.3, 11.4]   (0.1 min = 6 s wide)
SAMPLED on a 1-min grid: empty - neither t=11 nor t=12 is feasible
```

*Solver results*

| method | feasible dispatch set |
|---|---|
| hand calculation (sampled) | empty |
| grid sweep | empty |
| hand calculation (exact) | [11.3, 11.4] |
| exact interval solver | [11.3, 11.4] |
| independent brute-force oracle (same grid) | empty |

*Connected components*: 1 &nbsp;&nbsp; *Is a dispatch-by deadline*: **no** — report windows, not a deadline

> **The grid and the exact solver disagree here, and both are behaving correctly.** The grid is not wrong about its samples; it is silent about everything between them. Reporting the sampled answer as the feasible set would be the error.

**Comparison: PASS** — every method matches its own hand calculation.

**Scientific lesson.** A sampled empty result is **not** evidence of an empty feasible set. This is the counterexample that motivated the exact interval solver; see docs/TEMPORAL_RESOLUTION.md.
